# PayPal Partner — Merchant Onboarding Dashboard (gbox-emdash-admin)

**Status:** spec — implementation belongs to `gbox-emdash-admin` repo, Phase 2
**Owner:** Thai Bui
**Source of truth (PHP):** `gbox-paypal/includes/class-gbox-admin.php`
**Source of truth (TS API):** `gbox-platform/packages/core/src/modules/payments/paypal-partner/`
**Date:** 2026-04-08

## Why this spec exists

When the `gbox-paypal` PHP plugin was audited (commit `0f9e62a`, audit report sent
2026-04-08), `class-gbox-admin.php` was the **one piece that did not get ported**
to `gbox-platform` because it belongs in the admin UI, not the API. This spec
captures what it does so the work can be picked up cleanly when the
`gbox-emdash-admin` PayPal Partner plugin is built.

The corresponding API endpoints in `gbox-platform` already exist
(commits `3284772`, `0f9e62a`, `b1f7480`, and Step B/C of this audit), so the
admin plugin is **purely a UI on top of the existing REST routes** — no
backend work required.

## What the PHP did (`class-gbox-admin.php`)

A WordPress admin page mounted at `Tools → PayPal Partner` showing:

1. **Connection status** read from `user_meta` (single-tenant on Woo).
   On every page load it called `GBox_PayPal_API::get_merchant_integration_info($merchant_id)`
   to refresh `payments_receivable`, `primary_email_confirmed`, `products[]`.
2. **A read-only table** of:
   - Merchant ID (PayPal)
   - Merchant ID (Internal — Gbox tracking_id)
   - Permissions Granted
   - Account Status
   - Consent Status
   - Product Intent
   - Email Confirmed
3. **A `Connect with PayPal` / `Reconnect` button** generated by
   `GBox_PayPal_API::create_partner_referral_link()`.

## What the Gbox version must do

### Tab in store admin: **Settings → Payments → PayPal**

Per-shop, NOT per-user — Gbox is multi-tenant. Visible to roles **Store Owner** and
**Store Admin** (per CLAUDE.md hierarchy levels 2 & 3).

### Section 1 — Status card

Calls **`GET /api/store/:slug/paypal/status`** (already exists, returns
`{connected, merchant_id, reason, integration: {payments_receivable,
email_confirmed, products[]}}` after Step B). Renders:

| State                          | Badge  | CTA                              |
| ------------------------------ | ------ | -------------------------------- |
| Not connected                  | gray   | "Connect with PayPal"            |
| Connected, fully receivable    | green  | "Reconnect" (secondary)          |
| Connected but not receivable   | yellow | "Fix in PayPal" (deep link)      |
| Connected but email unconfirmed| yellow | "Confirm email in PayPal"        |
| API lookup failed              | red    | "Retry" + raw error in details   |

Show the merchant ID (truncated, copy-to-clipboard) and the list of `products[]`
(e.g. `PPCP_CUSTOM`, `PAYMENT_METHODS`).

### Section 2 — Connect / Reconnect button

Calls **`POST /api/store/:slug/paypal/onboarding`** with `{return_url}` set
to `https://admin.gbox.co/store/:slug/settings/payments/paypal/connected`.

Server returns `{onboarding_url}`. Open in a new tab so the merchant doesn't
lose admin context.

After PayPal redirects back, the URL fragment carries
`merchantIdInPayPal`, `merchantId`, `permissionsGranted`, `accountStatus`,
`consentStatus`, `productIntentID`, `isEmailConfirmed`. The admin SPA
parses the fragment and POSTs it to
**`POST /api/store/:slug/paypal/onboarding/callback`** (already exists).
On 200, refresh the status card.

### Section 3 — Test transaction (sandbox only)

If `PAYPAL_SANDBOX=true` and the merchant is connected, show a "Run test
charge ($1.00 USD)" button that:

1. POSTs to `/payments/paypal-partner/create` with a $1.00 dummy order
2. Pops up the PayPal sandbox approval URL in a modal iframe
3. POSTs to `/payments/paypal-partner/capture` after approval
4. POSTs to `/payments/paypal-partner/refund` immediately

This is the merchant's smoke test that everything is wired correctly
without touching real money.

### Section 4 — Recent transactions

Calls a future endpoint `GET /api/store/:slug/paypal/transactions?limit=20`
(NOT YET BUILT — track separately). Phase 2.5.

## What this spec is NOT

- Not a backend rewrite — all REST endpoints exist already.
- Not a billing/settlement view — that's Phase 3.
- Not a refund-management UI — refund route exists, but the orders module
  already has its own refund button. Wire the existing button to the
  Partner refund endpoint when the per-order detail page is built.

## Acceptance checklist

- [ ] Tab visible to Level 2/3 admins only
- [ ] Status card calls `/paypal/status` and renders all five states
- [ ] Connect button opens onboarding URL in new tab
- [ ] OAuth callback handler in admin SPA parses fragment + POSTs to callback
- [ ] After successful callback, status card auto-refreshes
- [ ] Test transaction button is gated on `PAYPAL_SANDBOX=true`
- [ ] All API calls use the admin SPA's existing fetch wrapper (CSRF + session)
- [ ] No PayPal credentials anywhere in admin SPA — server holds them
